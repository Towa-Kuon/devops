# 왜 굳이 이 도구들을 사용하는가

교안: 10. 왜 굳이 (2026-2 / 10주차). 아래는 교안의 설명을 짧게 정리한 내용이다.

## 배포와 Docker

배포는 만든 프로그램을 다른 사람이 사용할 수 있게 하는 과정이다. Docker 없이 서버에서 Python과 패키지를 설치하고 직접 실행할 수도 있다.

Docker는 프로그램과 라이브러리, 실행 설정을 이미지로 묶어 환경 차이를 줄이는 데 사용한다. 이미지가 운영체제 전체를 담는 것은 아니며 OS와 CPU 호환성도 고려해야 한다. (4~6쪽)

## WSL과 Ubuntu

WSL은 Windows에서 Linux를 실행하는 환경이다. Ubuntu는 그 안에서 사용할 수 있는 Linux 배포판 중 하나다. Windows에서도 Git과 Docker를 사용할 수 있으므로 Ubuntu만 정답은 아니다. (7쪽)

## Git과 GitHub

Git은 코드 변경 이력을 관리하고, GitHub는 저장소를 온라인에 보관하고 공유하는 서비스다. 웹에서도 수정할 수 있지만 여러 파일을 실행하고 테스트하며 관리할 때는 로컬 작업이 편리하다. (8쪽)

## 터미널

GUI는 사람이 마우스로 조작하기 편하다. CLI는 명령을 조합해 반복 작업을 자동화하기 쉽고, 원격 서버에서도 사용할 수 있다. 어느 쪽이 무조건 좋은 것이 아니라 상황에 맞게 고른다. (9쪽)

## Compose와 Kubernetes

Compose는 웹 서버, Redis, nginx 같은 여러 컨테이너의 실행 설정을 파일로 함께 관리한다.

Kubernetes는 원하는 복제본 수를 유지하고 장애가 나면 재생성을 시도한다. 모든 장애를 해결하거나 무조건 무중단을 보장하는 것은 아니다. 작은 프로젝트에는 Kubernetes를 쓰지 않는 편이 더 합리적일 수도 있다. (10~13쪽)

## 생각해 볼 질문

교안 15쪽의 질문에 대한 정리 예시다. 정답이 하나로 정해진 문제는 아니다.

상황 A: 혼자 만든 방명록을 서버 한 대에서 실행한다. 우선 실행 환경과 필요한 프로그램이 무엇인지 확인한다. Python 직접 실행으로도 가능하고, Redis까지 같이 관리한다면 Compose를 고려한다.

상황 B: 방문자가 늘어 여러 서버에서 운영한다. 여러 복제본을 배치하고 장애가 생긴 복제본을 다시 만드는 관리 문제가 생긴다. 이런 문제라면 Kubernetes를 고려할 수 있다.

## 앞으로 배울 내용

코드 수정 때마다 반복하는 테스트와 배포, 새 버전을 내보내는 방법, 문제를 발견하는 로그와 모니터링이 다음 주제다. 도구 이름만 외우기보다 해결하려는 문제부터 생각한다. (16~18쪽)

이 자료에는 별도의 실행 결과 제출 항목은 적혀 있지 않다. 실제 실습 과제는 함께 받은 배포와 서비스 교안 60쪽을 따른다.
